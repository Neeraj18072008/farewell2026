## what's inside

| area | route | what it does |
|---|---|---|
| invitation site | `/` | hero → gathering → what awaits → the night → same people. same vibes. new journeys. → venue → dress code → countdown → ready? |
| booking | `/book` | single / couple pass wizard (works even without javascript) |
| upi payment | `/pay/<token>` | QR code + amount generated from your UPI id, deep link for upi apps |
| digital pass | `/pass/<code>` | poster-styled pass with a huge 4-digit code — screenshot / print friendly |
| organizer login | `/organizer/login` | password-hashed accounts, brute-force lockout |
| control room | `/organizer` | stats · verify pass · bookings · pass-code inventory · activity · settings |

## quick start (local)

```bash
cd the-last-chapter
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python3 app.py            # → http://localhost:8000
```

the sqlite database, secret key and settings live in `instance/` (auto-created).

To clear test bookings before launch while preserving the printed-code inventory
and organizer accounts, run this deliberately destructive command once:

```bash
flask --app app reset-booking-data --yes
```

## configure your real prices + QR codes

control room → **settings**:

- `single pass price` / `couple pass price` — each pass type has its own price
- `upi id · single (QR 1)` / `upi id · couple (QR 2)` — the app generates the
  two QR codes from these ids with the correct amount prefilled
- `payee name` — what guests see in their upi app

placeholders ship by default — set these before sharing the link.

## money flow

- **cash** — booking is created `PENDING` → organizer taps *mark payment
  received* (at collection time) → `PAID` → entry allowed
- **upi** — guest scans QR, pays, taps *payment submitted* → status becomes
  `VERIFYING` → an organizer confirms receipt → `PAID` → entry allowed

entry at the door: **verify pass → guest details → allow entry**. a second
attempt on the same code shows **⚠ PASS ALREADY USED** — that's by design.

## deploy — github → render → live

1. push this folder to a github repo
2. on [render.com](https://render.com): **new → blueprint** → pick the repo
   (a `render.yaml` blueprint is included)
3. done — gunicorn serves the app

notes:

- the blueprint attaches a **1 gb disk** at `instance/` so the sqlite db and
  secret key survive deploys (disks need a paid instance — on the free tier the
  db resets on every deploy, fine only for testing)
- when the event outgrows sqlite, swap to postgres — only `store.py` touches
  sql, so the change is contained there
- set all three organizer-password environment variables in Render before the
  first boot; `SECRET_KEY` is generated by the blueprint
